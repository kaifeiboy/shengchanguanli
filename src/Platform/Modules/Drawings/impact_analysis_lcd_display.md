# LCD 屏显识别方案 — 代码改动定位与影响/风险分析

> 配套文档：`plan_lcd_display_region.md`（架构方案）、`verify_lcd_exemption.py`（实证验证）。
> 结论先行：**最小改动方案只动 1 个文件 `diff_visualizer.py`（Python），不碰 C#、H5、DB 架构、其它模块、端口**。对运行中平台几乎零中断、零重启。主要风险是「误检屏区域导致漏检真实缺陷」，已给出护栏。

---

## 1. 改动定位（文件 / 模块 / 函数）

方案核心：用**几何屏区域检测**替代「按文本内容豁免」，把"屏内文本"判为 display（灰，非缺陷），"屏外文本"判为 printed（走现有红/绿）。

| 改动 | 文件 | 位置（行） | 说明 |
|---|---|---|---|
| **新增** `_detect_display_regions(img_path)` | `diff_visualizer.py` | 新函数（建议接在 `_dense_rects` 后，~1062 后） | 复用 `_dense_rects`(1038) 作骨干，加屏专属过滤（高填充、边框、含文本、纵横比落在屏典型带）返回屏区域 bbox 列表（块图像素坐标） |
| **新增** 模块级缓存 `_display_region_cache` | `diff_visualizer.py` | 模块顶部 | key=(block_path, mtime)，避免每块重复计算 |
| **修改** `_compare_block` 签名 | `diff_visualizer.py` | 2073 | 增参 `block_display_regions=None`（调用方算好传入，保持函数"纯逻辑"） |
| **修改** `_compare_block` step4 | `diff_visualizer.py` | 2174–2235（灰化门控在 2223 `_is_cad_annotation` 处） | 块文本行质心落在某屏区域内 → `gray_block` + `cadOnly`，跳过红框判定 |
| **修改** `run()` | `diff_visualizer.py` | 2301；块图已在 2393 `Image.open(block_path)` | 在 2393 附近算 `display_regions` 并传入 `_compare_block`（2473） |
| **修改** `run_on_photo()` | `diff_visualizer.py` | 2617；`blk_path` 在 2711 已解析 | 把 2781 的 `_blk_ocr`（真实块图 bbox）提前，与屏区域一起传入 `_compare_block`（2730），使 8888 在 `_compare_block` 阶段即被灰化、**不进入 `red_block_info`** |

**坐标空间已核实一致**：
- `run()`：`block_lines` 来自 `_ocr_image(block_path)`(2379)，bbox 即块图像素坐标；屏区域同空间 → 质心判定直接成立。
- `run_on_photo()`：`block_lines` 来自 DB RawText，bbox 是**占位符 (0,0,10,10)**（见 2785 注释），不能直接做质心判定。必须用 2781 已算的 `_blk_ocr` 真实 bbox。==> 这是该路径最需要小心的点：将 `_blk_ocr` 提前并在 `_compare_block` 前完成屏区域+真实 bbox 的对齐，复用上一轮修红框偏移已验证的同一套机制。

### 明确**不在**改动范围（零影响）
`DrawingService.cs` / `OcrService.cs`（C#）、`index.html`（H5）、`Program.cs`、DB schema、启动脚本、端口、**其它模块 unbind / defecthistory**、冻结架构规则。H5 已有灰框渲染，只是"哪些文本算灰"变了，前端不用改。

## 2. 对运行中平台与模块的影响

### 2.1 部署 / 中断风险 —— **极低**
- `diff_visualizer.py` 由 C# 以**子进程**方式调用（`python diff_visualizer.py ...`）。本环境规则：**改 .py 即时生效，无需重启 Platform、无需重新编译**。下一次比对请求即加载新逻辑。
- 若改动含语法错误：仅该次子进程失败 → 该次比对返回 error；**Platform 主进程不崩**，unbind/defecthistory 等其它模块照常。属"单请求失败、可重试"，非中断。
- 无需 DB 迁移、无需改 schema（采用"惰性计算 + 缓存"而非"索引期落库"），故**无停机窗口**。

### 2.2 兼容性
- 对 **99 个块中绝大多数无 LCD 的产品**：检测不到屏区域 → 无文本被重分类 → 行为与今日**逐字节一致**。
- 仅 `did=112 blk=1` 的 `8888` 由红→灰（预期变化）。
- `validate.py` 基线需同步更新：当前断言 `R=28 Y=20 G=588 Gray=664`；8888 红→灰后应为 `R=27 G=588 Gray=665 Y=20`。必须改断言常量，并**新增定向断言**：除 did112-b1 的 8888 外，其余 27 张图纸 132 块的数量零变化 —— 这是"零负向"的硬证据。

### 2.3 性能影响 —— **可忽略**
- `_detect_display_regions` = 在小块图（如 441×459）上做阈值+轮廓，<5ms；且按 (path,mtime) 缓存，同产品多张照片只算一次。
- 不加载新模型，复用已 import 的 cv2/numpy/PIL。OCR（模型加载 ~3s）仍是主导，检测开销相对 <0.2%。

## 3. 可能引入的新问题 / 风险点

| # | 风险 | 方向 | 严重度 | 触发条件 | 护栏 / 缓解 |
|---|---|---|---|---|---|
| R1 | **误检屏区域 → 漏检真实缺陷（最危险）** | 准确率↓（漏报） | 高 | 某块含深色 logo / 图标底 / 深色标签矩形，被当作 LCD 面板 → 其打印文字被错误灰化，本应标红的缺失不被报 | ①屏判定加严：高填充+真边框+含文本+纵横比落在屏典型带（排除方标/圆标）；②**关键词护栏**：含 `服务热线`/型号前缀(`PC-`/`P1H`)/`HITACHI` 等永不灰化（即便落在深色区内）；③`validate.py` 断言 did106/107/115 等已知打印文本块**屏区域数=0** |
| R2 | **漏检真实 LCD → 8888 仍红** | 未改善（非退化） | 低 | 遥控器屏为细边框/浅屏/仅描边、检测器未命中 | 现状兜底：`_is_lcd_display_text` 词表+小数点规则保留作次级；小数 LCD(`88.`/`8.888`)仍按内容灰化。8888 仅"几何命中才修"，不命中=维持 today 行为，**绝不比现在差** |
| R3 | **`run_on_photo` 坐标空间错配** | 新 bug（偏移/失效） | 中 | 用 DB 占位 bbox(0,0,10,10) 做质心判定 → 8888 永不落入屏区域 | 复用 2781 `_blk_ocr` 真实 bbox（上一轮已验证对齐）；`_compare_block` 在 run_on_photo 下用真实块 OCR bbox 而非 DB 占位 |
| R4 | **屏内其实有打印标签（屏与铭牌同块）** | 准确率↓（漏报） | 中 | 屏边框内嵌型号丝印，被一并灰化 | 关键词护栏（R1-②）+ 仅当区块"高填充实心"才判屏，铭牌通常非实心填充 |
| R5 | **照片中屏是亮的（显示数字）** | 误判 | 低 | 实拍屏显示内容 → 与块图屏区域都"有文本" | 屏内容本就非打标，灰化属正确（非缺陷）；不影响 printed 文本比对 |
| R6 | **块图缺失/损坏** | 退化 | 低 | 块图文件读不到 | `_detect_display_regions` 包 try/except → 无区域 → 回退现状（8888 红），安全 |
| R7 | **资源消耗** | 内存 | 极低 | 缓存累积 | 99 块 × 每块几个 bbox ≈ 几 KB；按 mtime 失效，无泄漏风险 |

### 边界场景
- **多 LCD / 屏+标签共存块**：区域级判定只灰"屏矩形内"文本，标签保留 printed → 天然正确。
- **薄边框浅屏（命中失败）**：退化为现状（仍红），无新错误。
- **深色铭牌误命中**：靠 R1 几何加严 + 关键词护栏拦截；并以 validate 断言兜底。

## 4. 受影响范围总结

- **改动文件**：`diff_visualizer.py`（1 个，Python，~+60 行新函数 + 3 处调用点小改）。
- **不改动**：C# 全部、`index.html`、DB、`Program.cs`、端口、unbind、defecthistory、冻结架构。
- **运行影响**：即时生效、无需重启/重编；单请求失败可重试，平台与别模块不中断。
- **性能**：<5ms/块 + 缓存，可忽略。
- **质量风险**：集中在 R1（误检屏→漏报），已用"几何加严 + 关键词护栏 + validate 定向断言"三道护栏压制；R2/R3 不劣于现状。
- **回归保障**：改 `validate.py` 基线常量（R=27/Gray=665）+ 新增"仅 8888 翻转、其余 27 图零变化"断言。

---

## 5. 落地护栏建议（实施前确认）
1. 先写 `_detect_display_regions` 原型 + 对 99 块跑"屏区域检测报告"，人工核对仅 did112 命中、且 did106/107/115 等为 0（压 R1）。
2. 在 `_compare_block` 加屏灰化分支，先用开关 `ENABLE_DISPLAY_REGION_GRAY=False` 默认关，灰度验证后再开。
3. 跑全量 `validate.py`：确认 8888→灰、其余零负向；再上一轮 H5 照片端到端（did112）确认红框消失、坐标对齐。
4. 仅改 `diff_visualizer.py`，不动 C#/H5；生产 .py 覆盖即生效，无需重启。

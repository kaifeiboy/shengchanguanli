# 逻辑图块方案（把「图纸部位分离 v8.4」提升为正式逻辑图块体系）

> 本方案基于用户 2026-09-26 指令：**先做方案再实施**。本文档只做设计与清理清单，不改动任何生产代码。
> 前置事实来源：`tools/_extract_separate.py`（v8.4）八图实证基线、现有 C#/Python 代码实测盘点（见 §5）。

---

## 0. 方案定位

**逻辑图块 = 元素逻辑集合 + 一个包围盒**，不是物理切块。

已实证的部位分离算法（v8.4，八图基线 p50=5 / p52=6 / p56=2 / p57=2 / p61=5 / p62=5 / p64=5 / p67=6，sha256 全部零损伤）产出的是「图纸上哪个区域是一个独立产品部位」。本方案把它**从实验脚本提升为生产数据契约**：

- 图纸 PDF **不被裁剪、不被改写**（只读），元素保留**全局归一化坐标**；
- 每个元素被打上 `block_id` 归属标签 → 这就是「逻辑集合」；
- 图块自身只额外记录一个包围盒 `bbox_norm` 与块级元数据（视图提示、锚点表）；
- 「物理切图」（渲染 PNG、局部 OCR 裁剪）只在**运行时按需**发生，产物不入库为图块本体。

## 0.5 匹配范式（2026-09-26 16:52 用户拍板 · **最新，优先级高于 §1/§3 的配准设计**）

> 用户原话要点：①采用图块方式匹配后，**只需要把照片 OCR 后的内容去匹配图块中是否存在相关打标内容**；
> ②**图块可以用打标内容来命名**，后续匹配到这些内容即可直接命中；③命中后**只做准确性的标示**；
> ④**之前真值集的建立已经不合时宜**；⑤**只需保持之前的四色标示**。

### 0.5.1 匹配主链路（新）

```
照片
 └─ OCR → 文本串集合 {t1, t2, ...}（照片侧已能拿到文本 + bbox）
      └─ 【文本命中】拿 ti 去【图块的打标内容表】里查（**只查 has_marking=1 的块**，见 §2.1）：
             图块 A（name="型号:XXX / 服务热线:400-..."）  ← 以打标内容命名的块
             图块 B（name="CMIIT ID:..."）
             图块 C（...）
          → 命中哪个块 = 这张照片拍的就是哪个部位
      └─ 【标示】在该块内逐条比对打标内容 → 四色标示
```

**范式变化**：从「几何配准 + 位置映射」→「**文本命中 + 位置标示**」。

| 维度 | 旧范式（配准驱动） | 新范式（命中驱动，本次拍板） |
|---|---|---|
| 判定依据 | 图纸 mark 经仿射投影到照片后逐条比对 | **照片 OCR 文本是否命中图块内的打标内容** |
| 图块作用 | 提供锚点求仿射 | **提供「打标内容清单」供检索 + 提供标示位置** |
| 图块身份 | `view_hint`（视图名） | **`name` = 打标内容**（兼有 `view_hint` 作辅助/消歧） |
| 位置来源 | 图纸坐标 × 仿射 → 照片坐标 | **判定不依赖映射，但照片标示需要映射**（见 §0.5.5）：绿/黄取照片 OCR 的 bbox；**红（缺标）照片侧根本没有该文本 → 必须把块内元素位置映射到照片** |
| 产出 | 判定 + 映射后的标示 | **只做四色标示（准确性）** |

### 0.5.2 图块以「打标内容」命名（新）

- 块名 `name` 由**块内参与匹配的打标内容**（a/b/e 类文本）生成，例如：
  `型号XXX｜服务热线400-xxx｜NFC`、`CMIIT ID:xxxx｜面板丝印`、`二维码｜流水号SN`。
- 命名素材**排除 d 类**（尺寸/标注/说明）——与既有硬规则一致（用户拍板：说明性文字须舍弃，只有部位内部内容参与匹配）。
- ⚠ **空块（`has_marking=0`）没有 `name`**，也不参与命中检索（§2.1）。
- 块名同时作为**检索键**：照片 OCR 文本做归一化（去空格/全半角/大小写）后与块名/块内内容做**包含 + 编辑距离**双判据命中；
  命中即视为"照片属于该部位"，未命中任何块 → 整图兜底（保持现有行为，不引入新的失败模式）。
- ⚠ `name` 只是**人类可读标签**；机器判定仍以 `v2_block_elements` 的**逐条内容**为准（避免块名截断导致漏判）。

### 0.5.3 四色标示（保留，唯一产出）

| 色 | 含义 | 新范式下的判定 |
|---|---|---|
| 🟢 绿 | 一致 | 照片中该条打标内容与图纸**完全一致**（归一化后全等）。整体一个大绿框 |
| 🔴 红 | 差异 | **只标不同的那一段字符**：①部分字符不同 → 在绿框内把差异字符段标红（或分段标红）；②整条都不存在 → 整条标红。**不因「相似」就整条判红** |
| 🟡 黄 | 多标 / 不确定 | ①照片侧出现图纸**没有**的内容 ②照片 OCR 召回不足（有效文本 <3 条，`degraded`）导致无法确认 ③**QR / 图标：图纸与照片任一方不具备** |
| ⚪ 灰 | 跳过 | 仅剩 d 类：`dim`（线性尺寸）/ `meta`（图纸元信息：日期·版本·序号）/ `note`（说明文字）。不参与任何判定。<br>⚠ **QR / 图标已于 2026-09-27 移出灰类**，改走下方 §0.5.3.2 的存在性核对（绿/黄） |

**标示位置的三种来源（关键，见 §0.5.5 展开）**：

| 场景 | 照片侧标示位置 | 是否需要位置映射 |
|---|---|---|
| 🟢 绿 / 🟡 黄（照片上有该文本） | 直接取**照片 OCR 的 bbox** | ❌ 不需要 |
| 🔴 红（缺标：**照片上根本没有这条内容**） | 由**块内该元素的图纸坐标映射**到照片 | ✅ **必须** |
| QR / 图标（🟢/🟡） | 双方各自的 bbox（图纸 = 块内元素；照片 = `observe.codes[].bbox`） | ✅ 需核对位置是否在块投影区内（§0.5.5.2） |
| ⚪ 灰（d 类） | 块内 bbox（通常只在图纸画布标示） | 按需 |

图纸侧标示恒用**未变换的原始 `norm`**（既有坐标铁律，不因映射改变）。

### 0.5.3.2 三条标示口径（2026-09-27 用户重申，**覆盖先前 §0.5.3.1-B 的「相似 → 黄」**）

> 用户在批准 L0+L1 的同时重申了标示口径，以下三条为**当前唯一有效口径**，与旧文冲突时以此为准。

**规则 1 · 完全一致 → 🟢 绿**
照片中该条打标内容与图纸一致 → 整体一个**大绿框**（元素级，不需要字符级拆分）。

**规则 2 · 部分字符不同 → 🔴 红，只标差异处（本次新增，替代「相似判黄」）**

| 场景 | 旧口径（作废） | 新口径 |
|---|---|---|
| 相似但不等（Levenshtein ≤1） | 🟡 黄 | **🔴 红**，但**只框差异的那一段字符** |
| 一方包含另一方 | 🟡 黄 | 同上：公共部分绿，**多出/不同的字符段标红** |

允许的两种画法（由前端按密度自动选，用户已认可）：
- **绿内嵌红**：外层保留元素级大绿框（表示该部位已打标），内部对差异字符区间画小红框；
- **分段标红**：把该条文本按「相同段 / 差异段」切成若干子框，相同段绿、差异段红。

差异定位实现（照片侧）：照片 OCR 目前只给**整行文本 + 整行 bbox**，没有逐字符坐标，故采用
**字符索引 → 线性插值**：设该行 OCR 文本长度 `N`、bbox 宽 `W`，差异字符区间 `[i, j)` 在行内的占比
即其在框内的占比，得到子框 `x0 = bx0 + W*i/N`、`x1 = bx0 + W*j/N`（竖直方向同 bbox）。
- 该近似对中文/等宽排版足够准；同一条 OCR 文本内部通常同字号，中英混排的偏差在标示粒度上可接受。
- 后续若 OCR 换用支持字符级输出引擎（`paddleocr` 的 `rec_char_dict`/返回 char boxes），可直接取真实字符框替换插值。

**判定顺序**：先做元素级匹配（§0.5.3.1-B 的包含/编辑距离判据决定**这条算不算命中该部位**），
命中后再做字符级 diff 决定**框内哪几段标红**。两级互不影响。

**规则 3 · QR 与图标：只核「双方是否都具备」，QR 不读内容（本次新增，原「灰」作废）**

| 情形 | 判定 |
|---|---|
| 图纸块内有 QR/图标 **且** 照片对应位置也检出 | 🟢 绿 |
| **任意一方不具备**（图纸有 / 照片无，或照片有 / 图纸无） | 🟡 黄 |

- **不读 QR 内容**（图纸侧 25 条 Qr mark 的 text 实测全为 NULL，PDF 上是矢量示意图，本就无可比内容）。
- 图标同理，只比「有没有、在不在那个位置」，不比图案长得像不像。
- 照片侧数据源已具备：`observe` 的 `codes[]`（`zxingcpp` → `cv2-QR` → 分块扫描三级召回），带 `bbox`。
- 分两级实现，先粗后精：
  - **粗判（P3-b 可做，无需映射）**：图纸有 QR 而照片 `codes` 为空 → 🟡 黄；反之照片有 QR 而 Top 块内无 c 类元素 → 🟡 黄。
  - **精判（P4 做，需 L1 映射）**：把 c 类元素 bbox 经 L1 映射投影到照片，要求照片 QR 的 bbox 中心落在投影区内（含容差）才算「都具备」。


### 0.5.3.1 块命名规则与命中判据（2026-09-27 拍板）

**A. 块 `name` 命名规则**

| 项 | 规则 |
|---|---|
| 素材 | 块内 `participate=1` 的元素文本（a/b/e 类；c 类 QR 记为 `二维码`；**排除 d 类**） |
| 排序 | 按「从上到下、从左到右」阅读序拼接 |
| 分隔符 | `｜`（U+FF5C） |
| 单条截断 | 单条文本 >40 字符 → 取前 38 + `…` |
| 总长上限 | 120 字符；超出 → 保留前 N 条 + `…(+k 条)` |
| 重名消歧 | 同名块追加 `#2`、`#3`…；若 view_hint 不同则追加 `[view_hint]` |
| 空块 | 无 `name`（`has_marking=0`） |
| `name_fp` | 归一化后的 name（小写、仅保留字母数字、全角转半角），用于包含匹配；另存 sha256 前 12 位作精确去重键 |

**B. 命中判据（照片 OCR 文本 ↔ 块内打标内容）**

归一化：小写 + 去空格/标点 + 全角转半角。

| 情形 | 判定 | 颜色 |
|---|---|---|
| 归一化后**全等** | 命中 | 🟢 绿 |
| 长度 ≥6 且 Levenshtein **≤1** | 相似命中（不强判一致） | 🟡 黄（宁黄勿红，既有原则） |
| 长度 <6 | **必须全等**才命中，否则不算命中 | 🟢/— |
| 包含关系（一方含另一方）且短/长 ≥0.6 | 相似命中 | 🟡 黄 |
| 块内有、照片 OCR 无任何命中 | 缺标 | 🔴 红 |
| 照片 OCR 有、块内没有的打标内容 | 多标 | 🟡 黄 |
| 图标 / QR / d 类 | 不参与文本命中 | ⚪ 灰 |

多块命中时：取**命中条目数最多**的块为 Top1，保留 Top3 作候选（H5 可切换）；**不设命中率阈值**——命中即该部位，避免引入新的失败模式。

### 0.5.4 真值集：作废声明

- **此前判定"根卡点 = 无真值集"作废。** 新范式下判定链不依赖真值标注：命中即绿、不命中即红，准确率由**文本命中质量**决定，不由真值集决定。
- 因此 **P5（真值工具链验收 gates）整体取消**；依赖真值标定的 **M3 严格 Gate 自动放行**（confidence 需真值标定）**不再推进**。
- 质量保障改由**八图部位基线 + 文本命中回归**承担（基线已固化：`Scripts/eval/baseline_parts_v84.json`）。

### 0.5.5 照片标示位置映射（2026-09-26 补拍板：「照片标示还需要位置映射，要考虑到后续方案中」）

**为什么不能删映射**：🔴 红 = 缺标，意味着**照片上根本没有这条内容**，照片 OCR 给不出落点；要在照片上画出「这里少了一个标」，落点只能来自**图纸块内该元素的位置** → 必须做图纸 → 照片的坐标映射。
（同时：块级映射还能把**黄框/多标**的落点也统一到块坐标系，标示更整齐。）

**三级映射策略**：

| 级别 | 触发条件 | 做法 | 输出 |
|---|---|---|---|
| **L1 粗配**（默认必做） | 命中任一图块 | 块包围盒 `bbox_norm` ↔ **照片主体区域外接框**（照片侧取自现有主体检测 / 照片 OCR 文本并集）→ 求**平移 + 缩放**（相似变换） | `mapping=coarse` |
| **L2 精配**（条件启用） | 照片 OCR 文本中有 **≥3 条**能在块内找到对应元素 | 用这些「照片文本 ↔ 块内元素」对应点求**局部仿射** | `mapping=affine` |
| **L3 兜底** | 锚点 <3，或 L2 残差超阈值 | 退回 L1；仍不可靠则**照片侧不画框**，只在图纸画布标示 + 文字提示 | `mapping=none` |

**精度要求（比判定宽松）**：映射只服务**标示落点**，**不参与四色判定** → 判据建议：锚点残差中位数 ≤ 块对角线 3%（待标定）；超阈值即降级，**且映射失败不改变四色结论**（红仍是红，只是落点方式不同）。

**与既有资产的关系（改造复用，不删）**：
- `EstimateAnchorTransform` / `ApplyAffineRegistration`：**保留**，输入从「整页 mark 全集」换成「**命中块内的锚点子集**」，求解器本身不动。
- P0-2 基准点重构（`observe/geometry.py` 的 `corners` 与护栏）：护栏逻辑（guard-reject 时 `corners=null`）复用为 **L3 兜底判据**。
- ⚠ **整图级仿射在「未命中任何块」的整图兜底路径上仍须保留**（旧行为不动，避免回归）。

## 1. 逻辑图块的三个用途与落地路径

> ⚠ **已被 §0.5 修订**：用途 b 由「配准」改为「标示定位」（不再求跨图仿射）；用途 a 由「视图选块」改为「**打标内容命中选块**」。

| 用途 | 当前做法（痛点） | 逻辑图块做法 | 落点 |
|---|---|---|---|
| **a. 确定照片应该和哪个部位比** | 视图推断靠 mark 文本签名 + 盲检并集（`MarkVerifier.InferViewFromBlind`），部位归属不显式 → 视图正确率无法标定 | **【§0.5 改为】打标内容命中选块**：照片 OCR 文本检索块的 `name` / 块内内容清单 → 命中即该部位；未命中则整图兜底。`view_hint` 降为**辅助消歧与展示** | 新增块选择环节（compare 前置），`view_hint` 由块内文本 + 几何特征推断 |
| **b. 提供该部位的锚点和轮廓**（**改名：用于照片标示定位**） | 整图级仿射（`EstimateAnchorTransform` / `ApplyAffineRegistration`）：用**全部** mark 求一个全局仿射 → 单部位视角差会把整图带偏 | **【§0.5.5】三级映射**：L1 块包围盒粗配（平移+缩放）→ L2 块内锚点局部仿射 → L3 兜底不画框。**只服务标示落点，不参与判定** | 块级 `AnchorSet`；现有仿射求解器复用，只换输入子集（块内）+ 增加粗配/兜底分支 |
| **c. 限制匹配范围，降低噪声与计算量** | 全页 mark 参与判定；定点裁剪 OCR 面向整页/大区域 | 比对只在**目标块内**进行：块外 mark 不参与该次判定；局部 OCR 只渲染块 bbox | `MarkVerifier.Verify` 增加「块内子集」入参；`fallback` 渲染区域由块 bbox 驱动 |

## 2. 块内元素提取与分类（用户拍板 5 类）

| 类 | 内容 | 判定/提取方式 | 产出 | 参与匹配 |
|---|---|---|---|---|
| **a** | 正常矢量文本 | PDF 文本层 `get_text()` 直接取（现有 `VectorPdfParser` 已能做） | `kind=text`，text + bbox | ✔ 是 |
| **b** | 转曲文本 | **曲线区域检测**（`vpdf/fallback.py::find_char_regions` 已有）+ **高分辨率局部 OCR**：只渲染块 bbox 区域，300/400 dpi 双分辨率投票 | `kind=curve_text`，text（带 OCR 置信）+ bbox + `ocr_conf` | ✔ 是（低置信降级黄） |
| **c** | 图标 / QR | 只记位置与类型，**不提取内容** | `kind=icon` / `kind=qr`，bbox + center | ⚠ 仅验存在性与位置（与现有 `MarkType.Qr/Icon` 语义一致） |
| **d** | CAD 标注 / 尺寸 / 说明文字 | 现有 `MarkRules.IsDimension` + `_is_pure_explanation` + 说明性文字规则 | `kind=dim` / `note`，bbox，**保留在块内但不参与匹配** | ✘ 否（仅作部位选取辅助，用户拍板） |
| **e** | 栅格化文本 | 与 b 同路径（曲线区域检测对栅格区失效 → 走整块高分辨率 OCR 兜底） | `kind=raster_text` | ✔ 是 |

### 2.1 无打标内容的块（空块）不参与匹配（2026-09-26 用户拍板）

> 用户原话：**「无打标内容的块是不用参与匹配的，要确保提取及识别的准确性。」**

**定义**：块内**不存在任何参与匹配的元素**（a/b/c/e 类全无，只剩 d 类尺寸/标注/说明，或完全空白）→ 标记 `has_marking=0`。

| 项 | 规则 |
|---|---|
| 候选过滤 | `has_marking=0` 的块**不进入命中检索候选**，不产生红/绿/黄判定 |
| 是否删除 | **不删除、仍落库**（保留部位事实），只是 `participate=0` |
| UI 呈现 | 标注为「非打标部位 · 跳过」，与 ⚪ 灰（图标/QR/标注）区分开 |
| 典型例子 | 纯外形轮廓块、只有尺寸标注的块、只有说明文字的块、纯技术要求文字块 |

⚠ **这条同时是降噪手段**：八图基线 36 个块里若有一批空块，命中检索空间直接缩小，误命中概率下降。

### 2.2 「有没有打标内容」本身的准确性保障（关键，易错）

**最大的坑**：**文本层为空 ≠ 没有打标内容**。既有硬数据——132 条打标对象中 **39% 只能靠渲染 OCR 得到**（转曲/栅格化文本）。若只看 `get_text()` 就判空块，会**把真正的打标部位误杀**（漏判，比误判更严重）。

| 风险 | 后果 | 对策 |
|---|---|---|
| ① 文本层空就判空块 | **漏掉转曲/栅格打标部位**（严重） | **必须先跑块级局部高分辨率 OCR**，两路证据**都**没有才判 `has_marking=0` |
| ② OCR 参数降档求快 | 小字/型号码读不出 → 同上漏判 | 沿用既有铁律：**≥300dpi**、`det_limit_side_len ≥736`、双分辨率（300+400）投票；**不得用召回换时延** |
| ③ OCR 有结果但置信低就丢弃 | 真内容被判空 | 低置信**不算空**：`has_marking=1` + `low_conf=1`，命中时走**黄**（宁黄勿红，既有原则） |
| ④ 尺寸/说明文字被当内容 | 空块被误判为有内容（噪声） | d 类**永不计入** `has_marking`；块内只剩 d 类 → 空块 |
| ⑤ QR/图标算不算内容 | 口径不一 | **算**：激光打标的二维码是打标内容（`has_marking=1`），但标示走 ⚪ 灰（只验存在性与位置） |
| ⑥ **OCR 噪声串被当内容**（2026-09-27 用户实证） | 空块被误判为"有内容" → 比对时产生**假黄**，即用户要杜绝的"无内容块造成干扰" | **噪声判据**（见下）：OCR 来源串须通过有效性检验才计入 `has_marking`；**文本层不受此约束**（防误杀） |

**⑥ OCR 噪声判据（2026-09-27 新增，用户实证驱动）**

实证：`p67` 块内 OCR 出 `RK+n 2`、`VRF`、`2'0+88`（实为 `20±88` 误识别）；`p52` 出 `GD`、`GYD`——均为装饰纹/结构线的误识别，**不是打标内容**，却被当成内容进了命中库。

```
_is_valid_marking(t)  —— 仅对 OCR 来源（b/e 类）生效，文本层（a 类）不约束
  长度 < 2                        → 噪声
  含乱码符号 + ' ` ~ * & % $ # …  → 噪声          （RK+n 2 / 2'0+88）
  含 ≥2 连续中文                   → 有效
  纯字母 ≤3 位                     → 噪声          （GD / GYD）
  字母+数字混合 且 长度 ≥4          → 有效          （型号码 VH01GZ / YCTA113）
  纯数字 ≥3 位                     → 有效
  含 - _ . / : 且 长度 ≥5           → 有效          （02-HYXC-VH01GZ）
  纯英文 ≥4 位                     → 有效（保守保留，宁黄勿漏）
```

⚠ 误杀防线：①只作用于 OCR 来源；②英文 ≥4 位一律保留；③`丝印` 这类**工艺说明词**走 d 类 note 词表（已扩充：丝印/丝网/移印/烫金/镭雕/喷码/刻字/激光打标/打标内容），而非当内容。

`empty_reason` 新增取值 **`ocr_noise_only`**（OCR 有检出但全为噪声串），与 `all_dim_note` 区分，便于审计误判。

**空块判定流程**：

```
块 bbox
 ├─ ① 文本层证据：get_text() 里有非 d 类文本？        → 有 → has_marking=1
 ├─ ② 图形证据  ：块内有 QR/图标（c 类）？            → 有 → has_marking=1
 ├─ ③ 渲染 OCR  ：块 bbox 局部高分辨率渲染 + OCR（双分辨率投票）
 │                 有结果（含低置信）？                → 有 → has_marking=1（低置信记 low_conf）
 └─ ④ 三路皆空                                        → has_marking=0，记 empty_reason
```

`empty_reason` 取值：`no_text_layer` / `ocr_empty` / `all_dim_note`（便于事后审计误判）。

**成本与缓存**：③ 的局部 OCR 有开销，但**每块只算一次**并随块落库（`v2_logical_blocks.has_marking`），后续比对**直接读标记**，不重复渲染。

**回归方式（无需真值集）**：八图基线 36 个块逐块标注 `has_marking` 期望值 → 固化为基线的一部分，每次算法改动后全量核对。这是可人工核对的（"这块有没有打标内容"人眼可判），不依赖真值标注体系。

**关键约束（用户拍板硬事实）**：
1. 尺寸数字/标线**完全放弃**比对，只作选取部位的辅助手段 → 对应 d 类；
2. **说明性文字即使被分进图块也须舍弃**，只有部位内部内容参与匹配 → d 类在匹配层剔除，分图框容忍越界；
3. 转曲/栅格文本**不得用召回换时延**（既有教训：`det_limit_side_len` 480 会读错型号码，须 ≥736 + ≥300dpi）。

分类落库后，一条 mark 的判定链为：`block_id → kind → 是否参与匹配`。

### 2.3 空块在后期匹配比对时**不产生干扰**（2026-09-27 用户要求）

> 用户要求："能确保无内容的块后期匹配比对时不会产生干扰，即使无内容的块也没问题。"

**严格定义**：空块的存在与否，对任何一次比对的四色结论**没有任何影响**。

**三层隔离保障**：

| 层 | 机制 | 杜绝的干扰 |
|---|---|---|
| ① **命中库层** | 命中库**只装载** `has_marking=1` 的块内 `participate=1` 元素；空块**无内容可装载** | 🟢**假绿**：不可能"命中"一个空块 |
| ② **判定层** | 🟠红（块内有、照片没有）**只**对 `has_marking=1` 的块生成；空块不产生任何 verdict 行 | 🔴**假红**：空块不会凭空报缺标 |
| ③ **元素层** | d 类（尺寸/说明）与 OCR 噪声串 `participate=0`，不进库 | 🟡**假黄**：噪声串不会与照片文本"偶遇"匹配 |
| ④ **照片侧兜底** | 照片 OCR 文本在库中检索：命中→🟢；未命中→🟡黄（走人工确认，**不标红**，宁黄勿红既有原则） | 空块**不参与**未命中判定——照片文本是否命中与空块无关 |

**不变性验收（可自动回归）**：
1. 对任意空块 B 与任意照片文本 t：t **不可能**因 B 而命中（断言）
2. **删除/增加任意空块，四色判定结果逐条不变**（不变性测试）
3. 空块在 verdict 结果中**行数 = 0**

## 3. 锚点：块内具体内容 → **照片标示位置**

> ⚠ **用途已变更（§0.5.5）**：锚点**不再是判定的前置**（判定靠文本命中），而是 **L2 精配的输入**，用于把「缺标（红）」等照片侧没有落点的标示框**摆到照片的正确位置**。

**现状**：`AnchorTransform` 用整页 mark 集合求一个仿射（整体配准），单部位视角差会污染全局。

**新机制（命中 → 标示）**：

```
照片 OCR 文本
 └─ ① 命中选块：文本 ↔ 块内打标内容（name + elements）→ 命中块（Top1/Top3）
      └─ ② 四色判定（纯文本命中，不依赖坐标）：绿=命中 / 红=块内有但照片无 / 黄=照片多或相似 / 灰=不参与
           └─ ③ 标示落点：
                · 绿/黄 → 直接用照片 OCR 的 bbox
                · 红    → L1 块包围盒粗配（默认）/ L2 块内锚点局部仿射（≥3 对应点）/ L3 兜底不画框
                · 图纸画布 → 恒用未变换的原始 norm
```

**锚点选取规则（建议，需标定）**：
- 每个块选 **3~6 个**锚点：优先「文本长度 ≥4 且非数字纯标注」的稳定内容（型号、服务热线、警示语、编码）；
- 排除 d 类（尺寸/说明）与低置信 OCR 结果；
- 锚点记录 `anchor_norm`（中心）+ `text` + `conf`；几何均匀性要求：锚点在块内不过度共线（防仿射退化）；
- 锚点不足（<3）→ 退化为「块包围盒等价变换」（仅平移+缩放），并在结论里标记 `registration=coarse`。

### 3.1 view_hint 取值清单（部位级，2026-09-26 定）

> 用户拍板：**扩到部位级**（现有 `MarkView` 零件方位枚举装不下 PCB/QR 面）。
> 取值来自八图实证的部位构成（p50/p52/p56/p57/p61/p62/p64/p67）。

| view_hint | 含义 | 自动判定线索（可组合，按优先级） | 实证出处 |
|---|---|---|---|
| `TopView` | 顶视 / 上盖顶面 | 视图词含「顶视/上盖」+ 块内常带铭牌条（型号+服务热线+NFC）+ 宽扁比（w/h>1.5） | p61 P2、p64 P5、p62 顶视 |
| `Front` | 正面（屏/面板正面） | 块内含品牌丝印/大屏区域 + 型号 + CMIIT ID；面积占比大（≥7%） | p52 P3、p61 P1、p64 P2、p67 P2 |
| `Side` | 侧视（窄条） | 长宽比极端（窄条 w/h<0.35 或 h/w<0.35）+ 矢量少、文本少 | 全部八图均有（p67 P5、p52 P5…） |
| `Bottom` | 底视 / 底座面 | 视图词含「底视/底座/下盖」+ 常含打标二维码与流水号 | p67 P1、p61 P4、p64 P4 |
| `Back` | 背视 / 接线面 | 块内含接线标识（DC15/24V、禁止强电、LOW VOLTAGE、端子序号） | p52 P2、p61 P3、p64 P1 |
| `PcbBoard` | PCB 印刷板面 | 元件编号密集（R/C/U + 数字）+ 焊盘方阵 + 丝印编码，无外壳轮廓 | p67 P4(PCB)、p52 P4 |
| `QrFace` | 二维码打标面 | 块主体是二维码（图像 item 或密集矢量方阵）+ 邻近流水号文本 | p67 P6、p52 P2 |
| `Nameplate` | 铭牌 / 铭牌贴纸面 | 型号 + 服务热线 + 热线号成组出现，块小（<6%） | p50/p52/p61/p64 的铭牌条区域 |
| `Other` | 其它 | 以上均不命中 | — |
| `Unspecified` | 未定（缺省） | 证据不足，不参与自动选块 | 兜底 |

**与现有 `MarkView` 的关系（避免断裂）**：
- `view_hint` = **块级权威标签**（新）；`MarkView` = **mark 级粗粒度字段**（现有，`MarkVerifier`/`BlockMatcher` 仍在用）。
- 两者**共存 + 单向映射**（view_hint → MarkView），不做双向约束：
  `TopView/Front → TopCover`、`Bottom/Back/PcbBoard/QrFace → BottomCover`、`Side → Side`、`Nameplate → Nameplate`、`Other/Unspecified → Other`。
- ⚠ 映射**不唯一**（如 p67 的「底座」与「下视 QR 面」都映射 BottomCover）——这正是为什么选块必须用 `view_hint` 而非 `MarkView`。
- 现有 `MarkBuilder.InferView`(L674) 与 `BlockMatcher.InferView`(L51) 可复用为 view_hint 的**打分器**，只需把输入从 mark 集合换成块内元素集合，并补 PCB/QR/铭牌三类线索（元件编号密度、QR 图案、热线号组）。

### 4.2.1 两处实证修正（§0.5.3.1 的补充，均为真实照片驱动）

| # | 现象（实测） | 原判据的失败 | 修正 |
|---|---|---|---|
| ① | 照片 OCR 把整条铭牌读成一行 `PC-P1HVQ服务热线400-860-1111 NNFC`，块内是逐条元素 `服务热线400-860-1111` | 既不全等、长度比也 <0.6 → **全部漏命（假红）** | 新增判据 2：**照片串包含块内元素（needle ≥4）即命中**，与既有 `TextNormalizer.Contains`（打标项在实例文本中定位）同语义 |

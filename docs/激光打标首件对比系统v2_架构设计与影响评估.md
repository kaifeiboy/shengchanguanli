## 0. 结论摘要

1. **方案前提成立**：21 份原始图纸全部为**带原生文字层的真矢量 PDF**，可直接读取文字内容与坐标，无需整页 OCR。已实测验证（见 §2.2）。
2. **性能前提成立**：矢量原生解析平均 **291 ms/页**，相比旧「渲染→切块→块级 OCR」链路快 1～2 个数量级，且为**一次离线**行为，不占用在线匹配时间。
3. **架构主变更**：判定逻辑（Decision）从 Python 收回到 C#；Python 只保留「感知」（Perception：PDF 读取、照片 OCR/CV）。这是解决旧系统「不可追溯、不可测试」的根本手段。
4. **平台影响**：识别出 **2 个真实平台层违规耦合**，**P8 与 P7 均已修复并经 ≥2 角度验证**（见 §8.2）：
   - **P8**：`OcrService` 是事实上的平台共享设施（Unbind / DefectHistory 均注入），却注册在 `DrawingModule.cs:29`——换模块会导致**平台启动崩溃**。已按「新建平台设施、旧类封存」修复。
   - **P3**：`Program.cs` 直接依赖 `DrawingService` 具体类，违反 IModule 抽象。**按用户指示延后至 v2 完成后引入 `IStartupWarmup` 接口修复**（当前已有 `try/catch` 兜底，不会崩溃）。
   - 附带修复：看门狗 `tools\node` 悬空 Junction 导致平台无法自愈启动（§8.3）。
5. **入口保持不变**：H5 模块卡 `key=drawings`、路由前缀 `/api/drawings`、`drawings.Id` 主键语义全部保持，见 §7。

**架构含义（两条硬需求）**：
1. v2 **必须内置视觉兜底通路**：渲染 → 局部识别 → `source = "vision_fallback"` 标记（对应方案 §1 末句）。占比虽小但不可省。
2. **坐标系归一化必须处理页面方向**：19 份横版、2 份竖版，方向差异真实存在。
   ⚠️ 但归一化方式不是「统一转成横向」—— 见 §2.2c。

### 2.2c ★★ 坐标系真相（M1 实测，推翻了此前的旋转假设）

> 这一节记录 M1 阶段最重要的实证发现：**方案 §1 原句「页面坐标统一转换为横向标准坐标」
> 若按字面实现会直接导致坐标越界**。以下为实测结论，v2 全链路以此为准。

**实测事实（4 份样本：`YCWA15NCBQ` / `HYXC-VK01` / `10寸屏日立牌` / `10寸屏约克牌`）**

```
page.rotation      = 270
page.mediabox      = (0, 0, 595, 842)     <- 原始 PDF 空间（竖版 A4）
page.rect          = (0, 0, 842, 595)     <- 显示空间（横版）
get_text("dict")   span bbox x: 11..580   y: 8.6..844.58   <- 仍在**原始空间**
remove_rotation()  span bbox x: 8.6..844  y: 14.6..583.7   <- 显示空间
line dir           (0,1) -> (1,0)         <- 文字由竖排变横排
```

**结论**

1. PyMuPDF 的 `page.get_*()` 返回的是**未经旋转的原始 PDF 空间**坐标，
   与受 `/Rotate` 影响的 `page.rect` **不是同一坐标系**。
   （证据：mediabox 高 842 的页，bbox y 却达到 844.58，远超 `page.rect` 的 595。）
2. **正确做法**：先 `page.remove_rotation()`，再以 `page.rect` 作为标准坐标系。
   **不做「强制横向」**——2 份 10 寸屏图纸是**真实的竖版图纸**，强行旋转会把它们转错方向。
3. 页面朝向以 `orientation`（landscape / portrait / square）元数据记录，供渲染与 H5 按需处理。

**交叉验证（两个独立角度一致）**

| 角度 | 方法 | 结果 |
|---|---|---|
| A | `page.remove_rotation()` 后的 span bbox | 136 个 span |
| B | 原始空间 bbox 左乘 `page.rotation_matrix` 手算 | 136 个 span |
| 比对 | A == B | **完全一致（136/136）** |

**已落入代码的回归门禁**

- `vpdf/normalize.py` 顶部完整记录上述错误前提与修正过程（含判定依据）
- `vpdf/cli verify <sweepDir>` —— 断言所有 `norm_bbox ∈ [0,1]`、`bbox` 不越界且顺序正确
- 当前状态：`files=21 spans=1853 images=52 violations=0`

**附带收益**：修正后 `angle` 字段才成为可用特征（修正前全页面恒为假 90°）。
当前 21 份图纸的真实分布：`0°×1816 / 270°×33 / 180°×4`。

### 2.3 性能基线（实测，N=6）

| 解析动作 | 平均耗时 |
|---|---|
| `open` + `get_text("text")` + `get_text("words")` + `get_text("dict")` + `get_images` | **291 ms/页** |
| 上述 + `get_drawings()` | **1653 ms/页** |

## 3. v2 架构总览

### 3.1 本质差异

| 维度 | 旧系统（反面参考） | v2 |
|---|---|---|
| 图纸侧真值来源 | 渲染成位图 → 切块 → **对切块做 OCR 猜字** | **PDF 原生对象直读**，不猜字 |
| 业务数据单元 | 一张 PNG + 一坨 `RawText` | **应打标对象 `DrawingMark`**（结构化） |
| 块过滤 | `KeepViewBlock` 6 条硬编码阈值 | **视图语义划分 + 关键词/引线触发** |
| 物理切图 | 落盘 PNG，`drawing_blocks` 记录 → **成为事实数据源** | 渲染产物 = 可重建展示资源，**非数据源** |
| 通路 | `match-block`(新进程) / `match-and-photo`(常驻) 两套 | 单一 `inspect` 管道 |
| 缓存 | `_BLOCK_OCR_CACHE` 隐式跨请求缓存 | 无隐式缓存；只有已确认解析结果 |
| 匹配粒度 | 整块文本集合 diff | **对象级一对一**：粗筛图块 → 逐对象验标 |
| 结果表达 | 红/黄/绿/灰四色，无状态枚举 | **8 态枚举 + 逐对象原因与置信度** |
| 判定逻辑位置 | 散落在 Python 3703 行内 | **收敛到 C#**，Python 只做感知 |
| 可追溯 | 只有图 | 会话保存**当时对象清单快照 + 参数快照** |

### 3.2 分层与语言边界（关键决策）

```
┌──────────────────────────────────────────────────────────┐
│ H5 (手机端)   入口 key=drawings  ← 保持不变                │
└──────────────────────────────────────────────────────────┘
                          │ /api/drawings/...
┌──────────────────────────────────────────────────────────┐
│ C#  ── DECISION（决策层，可单测、可追溯）                   │
│   DrawingsV2Module      IModule 实现                      │
│   VectorPdfParser       消费中性 JSON（不绑定 PDF 库）      │
│   MarkBuilder           视图识别 + 应打标对象生成           │
│   ReviewService         人工确认/增删改对象                 │
│   BlockMatcher          找图块（粗筛）                     │
│   MarkVerifier          验标（对象级一对一）                │
│   VerdictAggregator     汇总 8 态 → 整体结论               │
│   V2Repository          存储                              │
└──────────────────────────────────────────────────────────┘
        │ 中性 JSON 契约（跨语言唯一接口）
┌──────────────────────────────────────────────────────────┐
│ Python ── PERCEPTION（感知层，无业务判定）                  │
│   vpdf/      矢量 PDF → 中性 JSON（独立库）                │
│   observe/   照片质量 / 文字 / 二维码 / 图标 / 轮廓         │
│   render/    标示图绘制                                   │
└──────────────────────────────────────────────────────────┘
```

**为什么这样切**：旧系统把「该不该判红框」的业务判定写进 Python，导致无法单测、无法追溯、改一处炸一片。v2 规定：**Python 只回答「我看到了什么 + 坐标 + 置信度」，永远不回答「合格还是不合格」。**

### 3.4 决策层实现现状（M2 已落地并验证）

> §3.3 是**规划**目录结构；M2 实际落地时做了收敛：**先把「决策层」做成一个可离线全量验证的
> 纯 C# 单元**（无 ASP.NET、无 IO、无 Python 依赖），再向上接端点。理由：决策正确性可以先于
> 集成被证明，避免"接了端点才发现判定是错的"。

实际落地（`src/Platform/Modules/DrawingsV2/Decision/`）：

| 文件 | 对应规划 | 说明 |
|---|---|---|
| `V2Models.cs` | `Domain/Enums.cs` + `Parsing/PageObjectModel.cs` | 契约对象与领域对象合并，避免为了分层而分层 |
| `VectorPdfParser.cs` | `Parsing/PyMuPdfBackedParser.cs` | 只消费 JSON；**schema 强校验** |
| `TextNormalizer.cs` | `Matching/TextNormalizer.cs` | 提前，因为构造 mark 时就要用 |
| `MarkRules.cs` + `MarkBuilder.cs` | `Building/` | 规则表与构造器分离，规则可独立扩充 |
| `V2Store.cs` | `Storage/V2Repository.cs` | 独立库 `drawingsv2.db`（**不复用 app.db**，比规划更彻底） |

**与规划的两处偏离（有意为之，理由如下）**

1. **独立库而非 `app.db` 加前缀表** —— 规划 §P6 已要求"不 ALTER/不 DELETE 既有表"，
   但同库仍有文件名锁争用与误操作风险。改为独立 `drawingsv2.db`（与 `InvTail` 的
   `invtail.db` 一致），对其它模块的影响从「低」降为「零」。
2. **Group 不单独建表**（原规划有 `MarkGroup.cs`） —— 用 `v2_drawing_marks.parent_id` 自关联。
   子项本身是完整 mark（有自己的 rule / 置信度 / 证据），单表自关联少一次 join 且保留逐项可追溯。

## 4. 数据模型

命名决策：**新增表全部 `v2_` 前缀**，与旧表物理隔离，回滚只需 `DROP TABLE v2_*`；`drawings.Id` 继续作为图纸身份主键（保证 H5 `/detail/{id}` 与历史记录兼容）。

```sql
-- 图纸解析档案（1:1 关联旧 drawings.Id，不改旧表）
CREATE TABLE IF NOT EXISTS v2_drawing_profiles (
  Id            INTEGER PRIMARY KEY AUTOINCREMENT,
  DrawingId     INTEGER NOT NULL UNIQUE,
  FileHash      TEXT NOT NULL,        -- SHA256：变更检测 + 去重
  PageCount     INTEGER,
  PageWidth     REAL, PageHeight REAL,
  Status        TEXT NOT NULL,        -- pending|parsing|parsed|reviewed|failed
  ParseError    TEXT,
  ParserVersion TEXT NOT NULL,        -- ★ 解析器版本，结果可复现
  ReviewedAt    TEXT, ReviewedBy TEXT,
  CreatedAt TEXT, UpdatedAt TEXT
);

-- 视图（产品视图 / 打标区域）
CREATE TABLE IF NOT EXISTS v2_drawing_views (
  Id INTEGER PRIMARY KEY AUTOINCREMENT,
  DrawingId INTEGER NOT NULL,
  ViewKey TEXT NOT NULL,              -- top_cover / bottom / side / panel ...
  Label TEXT,
  BBox TEXT NOT NULL,                 -- JSON [x,y,w,h] 页面坐标
  NormBBox TEXT NOT NULL,             -- JSON [x,y,w,h] 归一化 0..1
  Rotation REAL DEFAULT 0,
  SortOrder INTEGER DEFAULT 0
);

-- 应打标对象（★ v2 的业务核心）
CREATE TABLE IF NOT EXISTS v2_drawing_marks (
  Id INTEGER PRIMARY KEY AUTOINCREMENT,
  DrawingId INTEGER NOT NULL,
  ViewId INTEGER,
  GroupId INTEGER,
  MarkId TEXT NOT NULL,               -- 业务 id，如 top_text_01
  MarkType TEXT NOT NULL,             -- text|qr|icon|group
  Text TEXT,
  Required INTEGER NOT NULL DEFAULT 1,
  Condition TEXT,                     -- 适用型号 / 适用条件
  BBox TEXT NOT NULL,                 -- 页面原始坐标
  NormBBox TEXT NOT NULL,             -- 归一化，跨渲染比例映射
  Direction REAL DEFAULT 0,
  Source TEXT NOT NULL,               -- pdf_vector|vision_fallback|manual
  Confidence REAL DEFAULT 1.0,
  FontSize REAL,
  FormatRule TEXT,                    -- 可变化文字的格式规则（日期/批次/流水号）
  CreatedAt TEXT
);
CREATE INDEX IF NOT EXISTS ix_v2_marks_drawing ON v2_drawing_marks(DrawingId);

-- 对象组（同一打标区内的多行文字/二维码/图标）
CREATE TABLE IF NOT EXISTS v2_drawing_mark_groups (
  Id INTEGER PRIMARY KEY AUTOINCREMENT,
  DrawingId INTEGER NOT NULL,
  GroupKey TEXT NOT NULL,
  Label TEXT,
  BBox TEXT NOT NULL, NormBBox TEXT NOT NULL
);

-- 匹配会话（一次检验，可含多张照片）
CREATE TABLE IF NOT EXISTS v2_match_sessions (
  Id INTEGER PRIMARY KEY AUTOINCREMENT,
  DrawingId INTEGER NOT NULL,
  MarksSnapshot TEXT NOT NULL,        -- ★ 当时对象清单 JSON（可追溯硬要求）
  ParamsSnapshot TEXT NOT NULL,       -- ★ 当时匹配参数 JSON
  ParserVersion TEXT, MatcherVersion TEXT,
  Operator TEXT,
  Verdict TEXT,                       -- pass|review|fail|error
  CreatedAt TEXT
);

-- 照片观测
CREATE TABLE IF NOT EXISTS v2_match_observations (
  Id INTEGER PRIMARY KEY AUTOINCREMENT,
  SessionId INTEGER NOT NULL,
  PhotoPath TEXT NOT NULL,
  QualityJson TEXT NOT NULL,          -- 清晰度/亮度/主体占比/遮挡
  QualityPass INTEGER NOT NULL,
  ObservationJson TEXT NOT NULL,      -- 观测到的 text/qr/icon（含坐标+置信度）
  CreatedAt TEXT
);

-- 对象级结果（★ 可追溯的最小单元）
CREATE TABLE IF NOT EXISTS v2_match_results (
  Id INTEGER PRIMARY KEY AUTOINCREMENT,
  SessionId INTEGER NOT NULL,
  MarkId TEXT NOT NULL,
  Status TEXT NOT NULL,               -- 8 态枚举
  RequiredValue TEXT, ObservedValue TEXT,
  Confidence REAL,
  Reason TEXT,                        -- 人话解释
  PhotoBox TEXT, DrawingBox TEXT,
  CreatedAt TEXT
);
CREATE INDEX IF NOT EXISTS ix_v2_results_session ON v2_match_results(SessionId);
```

### 状态枚举（严格按方案 §8）

```
matched          已找到，文字逐字一致 / 二维码图标存在且位置正确
missing          图纸要求，照片没有
wrong            文字错误，或明确位置错误
extra            照片有，图纸没有
low_confidence   识别置信度不足 / 照片质量不足 → 待复核
not_applicable   不适用（条件不满足，如非指定型号）
not_comparable   未拍到该部位 / 当前无法比较
processing_error 处理异常
```

**汇总规则**：存在 `missing`/`wrong`/`processing_error` → **不通过**；无红但存在 `low_confidence`/`extra` → **待复核**；全部必检对象 `matched` → **通过**。

## 5. 核心流程

### 5.1 图纸侧（离线，一次）

```
上传/同步 PDF
  → 计算 SHA256，查 v2_drawing_profiles
  → [变更或首次] vpdf 解析（291ms/页）
        · 归一化坐标系（统一横向）★ 19 横版 / 2 竖版，必需
        · 提取文字 span（内容+坐标+字号+旋转）
        · 提取图像对象（二维码/图标候选）
        · [按需] get_drawings 检测引线（仅当触发规则要求，+1.4s）
  → 【分支】原生文字层判定（words >= 20）
        ├─ 命中（19/21，90.5%）→ 走矢量路径，source = "pdf_vector"
        └─ 未命中（2/21，转曲）→ 渲染 200DPI + 局部视觉识别，
                                   source = "vision_fallback"，confidence 降级
  → MarkBuilder 生成对象
        · 排斥区：标题栏 / 修订记录 / 图纸编号 / 技术要求的"非打标句" / 发放部门 / 普通尺寸公差
        · 触发区：出现「激光打标」「镭雕」「服务热线」「二维码」「MAC」或存在指向产品表面引线
                  → 取邻近文字/图像为候选对象
  → 写入 v2_drawing_views / v2_drawing_marks
  → Status = parsed，等待人工确认
  → 人工确认后 Status = reviewed，才允许生产匹配
```

### 5.2 照片侧（在线）

```
照片上传
  → [Stage 1] 质量检查：清晰度 / 亮度 / 主体占比 / 遮挡 / 目标完整性
       不合格 → 返回 "请重新拍摄"，【不判缺标】★
  → [Stage 2] 感知（Python observe）
       · 旋转校正 / 透视校正 / 尺度归一化
       · 文字区域 → 逐字符坐标 + 置信度（不只返回整串）
       · 二维码 / 图标 → 存在性 + 外接矩形 + 中心 + 方向
       · 轮廓 → 边框/孔位/面板结构基准点
  → [Stage 3] 找图块（C# BlockMatcher，粗筛）
       依据：固定文字集合 / 文字布局 / 二维码数 / 图标数 / 相对位置 / 轮廓长宽比
       唯一候选且达阈值 → 自动进入下一步
       多候选接近     → H5 让用户选部位
  → [Stage 4] 验标（C# MarkVerifier，对象级一对一）
       · 文字：安全归一化 → 逐字比较 → 输出正确/错误/缺失/多余区段
       · 可变化文字：按 FormatRule 校验长度/字符范围/格式
       · 二维码/图标：只比存在性与位置
  → [Stage 5] 汇总 + 标示（渲染到照片与图纸块，同一对象状态）
  → [Stage 6] 入会话；可继续上传其它部位，合并到同一次检验
```

### 5.3 文字匹配规则（严格按方案 §6）

- **只做安全归一化**：全角半角统一、大小写统一、首尾空格清理、连续空格合并。
- **不随意替换**数字/字母/斜杠/连字符/加减号/直径符号/单位。
- `0/O`、`1/I` 等易混字符 → 记为 `low_confidence`，**不得直接视为相同**。
- 固定文字逐字一致；可变化文字按 `FormatRule` 校验。
- 结果保存**正确/错误/缺失/多余字符区间**，渲染只标示对应区段。

## 9. 实施路线（建议分 5 期）

| 期 | 目标 | 产出 | 平台影响 |

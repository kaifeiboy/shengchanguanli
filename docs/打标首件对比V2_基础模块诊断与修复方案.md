# 打标首件对比 V2 · 基础模块系统诊断与修复方案

> 目的：按用户要求，对 4 个基础模块（①照片预处理 ②图纸部位区分 ③产品部位匹配与对比 ④打标内容识别与标示）做**系统诊断 + 修复方案**，**先确认再改**。
> 诊断方法：每个根因均取「代码静态证据 + 真实 DB/基线 实证」两个独立角度交叉验证（遵循项目事实验证硬规则）。
> 实证来源：`data/drawingsv2.db`（18 份档案视图分布、`is_active` 泄漏）、`baseline_report_p6.json`（42 例最新基线）。

---

## 0. 一句话结论

「连最基本的产品部位都无法完整匹配」的根因不在某个环节，而在**模块②从未真正实现设计 §4/§5 的「图块（产品部位）几何实体」**，而是用「图纸上离 mark 最近的视图词文本块」做启发式猜测。图纸不在 mark 附近印视图词 → mark 无部位 → `Unspecified`；照片侧又靠型号码/QR 反推部位，缺这些就退化成整页比对。下游 ③坐标映射与 ④内容标示全部建立在「部位=视图词并集」这个不稳的假设上，于是**部位一旦分不清，后续全废**——这正是用户描述的「后期标示成无用功」。

## 1. 模块① 照片预处理流程

### 现状（代码证据）
- `observe/pipeline.py`：`MAX_SIDE=1280` 把整图缩到 1280 长边后再做 OCR（注释实测 1280 比原图省 1/3 时间、只少 4 个区，但少的是尺寸标注类噪声）。
- `observe/quality.py`：质量门 `assess()` 硬阻断「短边<640 / 过曝 / 过暗 / 动态范围<30」；`apply_ocr_evidence()` 仅把**清晰度、灰阶动态范围**两类统计门槛降级为提示（OCR 取到内容才放行），**分辨率/过曝/过暗仍硬阻断**。
- `observe/geometry.py`：`detect_quad` 找不到可信四边形 → `no-quad`；平坦图（四角贴边/轴对齐）→ `flat-quad-skip` 不矫正。失败即降级，不硬猜。

### 根因
- **RC1.1（小内容细节损失）**：整图压到 1280 后再定点 OCR，细长打标串（MAC 码、端子标识）在缩图下面积更小、更易漏检/误识（实测 NAC↔MAC、地暖阀↔地暖烟 单字误识）。这是模块④判不准的上游之一。
- **RC1.2（质量门偏脆）**：分辨率/过曝/过暗是硬阻断，但「金属壳+激光刻字」这类高局部对比、整体中灰的照片，或手机近距离拍的小部件照，可能被灰度统计误伤；而真正不可读的照片又可能因 OCR 侥幸命中一处而被放行。

### 实证
- 基线 `photoUsableRate=100%`——当前 42 例未触发阻断，但门逻辑对「合格零件照」的鲁棒性未经负样本验证；`MAX_SIDE=1280` 取舍注释本身承认「开始丢内容」的风险。

## 2. 模块② 图纸部位的区分逻辑（核心病灶）

### 现状（代码证据）
- `MarkRules.ViewWords`：部位枚举**只有 5 类**——`上盖/面板/顶部→TopCover`、`下盖/底部→BottomCover`、`后盖/侧面→Side`、`接线/线材→Cable`、`铭牌→Nameplate`。
- `MarkBuilder.InferView()`：给每个 mark 分配视图 = 在整页里找**离该 mark 最近**的「含视图词文本块」（排除 clause/revision，保留 qrDecl）。找不到 → `MarkView.Unspecified`。
- `BlockMatcher.InferView()`（照片侧自动选部位）：对图纸各视图的 marks 聚合特征签名（型号码/QR/固定文本/质心），与照片盲检特征多特征加权打分；`Chosen` 须 `score≥1.6×Top2` 才自动选，否则 `Chosen=null` → **退化整页比对**。

### 根因
- **RC2.1（设计背离·核心）**：设计 §4/§5 要求提取「图块（产品部位）几何实体」作为一级对象（带自身坐标系），现实现**完全没有图块提取**，用「邻近文本猜部位」替代。图纸若不在 mark 附近印视图词（很多图纸只用「图一/A向/section 字母」或在技术要求里提一次），mark 即无部位。
- **RC2.2（枚举过粗）**：真实产品部位远多于 5 类（左盖/右盖/前壳/主板/电源板/具体命名区…），写死的 5 类无法表达多数产品的真实部位，导致部位被强行并入 TopCover/BottomCover。
- **RC2.3（照片侧退化）**：`BlockMatcher` 靠型号码/QR/区别文本打分。一张**只拍了标签区、不含型号码也没有 QR** 的零件照，拿不到足够特征 → `Chosen=null` → 与整张图纸所有部位的所有 mark 逐一对比较 → 无法聚焦重点、噪声与漏检齐发。

### 实证（DB）
- `v2_drawing_marks` 视图分布：
  - **p58 约克86彩屏线控器**：4 个 mark **全部 `Unspecified`**（部位区分彻底失败，典型「连最基本部位都分不出」）。
  - p62：1 个 `Unspecified`（混入）。
  - 其余多为 `TopCover/BottomCover` 二元，反映枚举过粗、部位被压扁。
- 基线 `viewLabeled=0` → `viewAccuracy=null`：真值集**未标注部位**，意味着目前根本无法量化「部位区分对错」，修复也无从回归。

## 3. 模块③ 产品部位的匹配与对比算法

### 现状（代码证据）
- `V2Service.CompareCoreAsync`：选/推部位 → `FilterByView` → `ViewBboxOf(filteredMarks)`（取视图标签块 bbox 与同视图 marks 并集）→ `RebaseToView(mark.NormBbox, viewBbox)`（页面坐标→视图局部坐标）→ `ApplyAffineRegistration` → `EstimateAnchorTransform`（文本/QR 锚点估平移/尺度）→ `VerifyAsync` 定点 → `MarkVerifier.Verify` → `#27 EstimateConsistentOffset` 重裁。
- `MarkVerifier.ViewBboxOf`：视图包围盒 = 视图标签块 bbox ∪ 距其 `maxDist=1.0`（极宽松）内的同视图 marks 并集。
- `EstimateAnchorTransform`：单锚点只平移；≥2 锚点估均匀尺度+质心对齐；**≥3 锚点且残差>0.10 才抑制**，1~2 锚点不 gate。

### 根因
- **RC3.1（坐标假设过强）**：整套映射假定「**照片 = 该视图区域包围盒**」。视图包围盒由 marks 并集推算，若照片只拍了部件一角、有倾斜、或取景偏移，重映射后的定点坐标就落在照片错误位置 → 定点区罩空白 → 内容检不到 → `NotDetected`。这是 33.5% 未检出率的主要来源。
- **RC3.2（配准只到相似变换且保护不足）**：仅平移/均匀缩放，无旋转/斜切校正；1~2 锚点病例**不做残差 gating**，坏变换仍生效（p63 曾现 `dx=-3.26/scale=4` 顶限幅的错配，#24 gate 只拦了 ≥3 锚点情形）。
- **RC3.3（`is_active` 不生效）**：`V2Store.ReadMarkRows` 不过滤 `is_active`，被人工取消（软删）的误提取 mark 仍参与比对、仍出现在 verdicts。

### 实证（DB + 基线）
- 基线 `verdictDistribution`：Matched 78 / **NotDetected 58（33.5%）** / LowConfidence 37 / NotApplicable 60；`recall=77.1%`。
- `#27` 离线剖析：p63 系列 7 例多项「全图实际检出位置 − 图纸映射位置」偏移高度一致（dy 极差 0.005~0.014，量约 (-0.6,+0.6)）——证明映射本身系统性偏，非随机误差。
- DB：`is_active=0` 的 mark 仍出现在 `v2_compare_verdicts` 中（已知缺陷，42 个未生效）。

## 4. 模块④ 打标内容的识别与标示

### 现状（代码证据）
- `MarkVerifier.VerifyText`：先查定点区 `obs.Texts`；命中则三级匹配（Exact/Normalized 判绿，Ambiguous/疑似误识判黄）。**若 `obs.Texts` 为空**：几何未配准则全图盲检兜底（仅判黄 LowConfidence，绝不判绿），已配准则同样盲检兜底判黄；都无 → `NotDetected`/`Missing`。
- `MarkRules.MatchKeysOf`：匹配键 = 声明项本体 + 去后缀 + `Aliases` + `KnownContent`（有限词表）。

### 根因
- **RC4.1（连锁失效·核心）**：`VerifyText` 能否判绿**完全依赖定点区 obs 里有文字**。只要模块②③坐标错位导致 obs 罩错位置（obs.Texts 空），就只剩盲检兜底 → **最多黄、永远绿不了**。即「部位没匹配对 → 内容标示必废」，与用户原话一致。
- **RC4.2（键表覆盖有限）**：新图纸/英文变体写法若不在 `KnownContent`/`Aliases`，即便坐标正确也无匹配 → 黄/红。
- **RC4.3（H5 标示坐标）**：照片画布用 `v.PhotoBbox` 实际检出位置回填（逻辑已修「只兜底不覆盖」），但标注画布 UI 元素仍受坐标缩放陷阱影响（历史坑：手柄半径须按屏幕像素/scale 换算），属前端呈现，不在本次后端修复主链。

### 实证
- `VerifyText` 第 889–938 行：盲检兜底分支证据文案明确写「几何未配准/视图级配准位置可能有偏差，需人工复核」且 state 恒为 `LowConfidence`，证实坐标错位即判不了绿。

## 5. 修复方案（地基优先，分阶）

> 顺序即依赖：②是基础，③承接②的坐标基准，④承接③，①是上游。P5 真值基线是全部修复可回归的前提。

### Phase 0 — 补可验证真值基线（P5 前置，必做）
- 构建「视图级真值」：每张照片标注其对应 `view` + 每个 mark 在照片上的真实状态（green/red/yellow/na）。
- 目标：`viewLabeled>0` → `viewAccuracy` 可计算，修复有回归闸门。
- 产出：`Scripts/eval/truth_*.json` 真值集 + `run_baseline.py` 增加部位准确率指标。

### Phase 1 — 模块② 部位区分（核心，回到设计 §4/§5）
- 实现「图块（产品部位）几何实体」提取：从 `vpdf` 矢量图形/图像对象 + 视图标签，识别每个部位的**几何包围区域**（而非靠邻近文本猜）。
- 部位标识从「写死 5 枚举」改为「读取图纸视图标签文本」的自由部位名（兼容现有枚举映射）。
- 每个 mark 绑定到所属图块的几何区域，作为后续坐标基准。
- 照片侧 `BlockMatcher` 改用「图块几何 + 部位内特征」匹配，降低对型号码/QR 的硬依赖。

### Phase 2 — 模块① 照片预处理
- OCR 输入策略：定点识别小打标内容时用**原图/更高分辨率裁剪**（保留 RapidOCR 小裁剪加白边修复），不再整图压 1280 后盲检。
- 质量门：仅对真正不可读（分辨率/过曝/过暗）阻断；清晰度/动态范围维持 OCR 证据豁免（已做）；补负样本验证门限。

### Phase 3 — 模块③ 匹配与对比算法
- 坐标基准由「视图词并集」换为 Phase1 的**图块几何区域**（照片映射到图块，而非整页/整视图）。
- 锚点配准升级为**相似/仿射变换（含旋转/斜切）**，并重审 1~2 锚点病例的 gating（避免坏变换生效）。
- 修复 `is_active` 不生效：`LoadMarks`/`ReadMarkRows` 过滤 `is_active=0`（注意区分「复核页读取」与「比对读取」两个入口）。

### Phase 4 — 模块④ 内容识别与标示
- 坐标正确后 `VerifyText` 自然能稳定判绿；补充 `KnownContent`/`Aliases` 覆盖（来自 Phase0 真值里的新写法）。
- H5 标示坐标走照片实际检出位置（已修逻辑），前端标注画布按 scale 换算手柄/线宽。

## 6. 风险与前提
- **真值缺失是总前提**：当前 `viewLabeled=0`，不先补 Phase 0，任何修复都无法量化「部位区分对错」，违背项目「根因双角度 + 修复须回归」硬规则。
- **架构级改动**：Phase 1/3 涉及坐标基准重构，属模块内改动（不动平台/其它模块），但需逐 Phase 回归、单 Phase 交付。
- **`is_active` 修复虽小但影响比对口径**：修复后现役 42 个被取消 mark 不再参与，历史记录不受影响（有 marksSnapshot）。

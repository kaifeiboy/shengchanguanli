# 打标首件对比模块（drawings）技术文档

- **版本基准**：git HEAD `97ba42a`，匹配引擎 `_debugVersion = v19.56`

## 1. 模块定位

打标首件对比：把**图纸 PDF 切割成块（block）**并入库，再将**产品实拍照片**与块做内容比对，输出四色标示图（红/黄/绿/灰）与匹配结论，用于产线首件检验。

| 角色 | 位置 |
|---|---|
| H5 前端 | `src/Platform/wwwroot/index.html` |
| API 层 | `src/Platform/Modules/Drawings/DrawingModule.cs` |
| 业务层 | `src/Platform/Modules/Drawings/DrawingService.cs` |
| OCR 服务层 | `src/Platform/Modules/Drawings/OcrService.cs`（含常驻 worker 客户端） |
| 分割 | `segment_blocks.py` + `segment_blocks_auto.py` + `pp_doclayout_onnx.py` |
| 比对/绘制 | `diff_visualizer.py`、`photo_registration.py`、`ocr_cli.py`、`resize_photo.py` |

```

│  PDF → PyMuPDF 渲染(200 DPI) → PP-DocLayoutV3 ONNX 检   │
│  测 → 规则过滤 → 裁切 PNG → manifest.json → 批量 OCR    │
│  → KeepViewBlock 过滤 → 入 drawing_blocks → 写 .done    │
└──────────────────────────────────────────────────────┘
                          ▼
┌─ 阶段 B：照片比对（每次请求）──────────────────────────┐
│  H5 POST /match-block (45s abort)                      │

```

## 3. 图纸分割（Segmentation）

### 3.1 触发时机与幂等

| 入口 | 说明 |
|---|---|
| `MatchBlock` 调用 `EnsureSegmented`（`:1794`） | 比对前懒加载，已切过则直接返回 |
| `POST /api/drawings/segment`（`DrawingModule.cs:192`） | 指定 drawingId 同步切；省略则后台批量切全部 |
| `POST /api/drawings/refilter`（`:214`） | 重过滤（不重切） |
| `Warmup`（`:1562`）/ `SegmentAll`（`:1615`） | 后台批量 |

- **幂等标记**：`data/seg/<did>/.done` 存在即视为已切（`BlocksCached` `:1214`）。
- **force 重切**（`:1221-1229`）：删除 `.done` → 清 `_blockCache` → 清 `_blockBboxCache` 中 `did_` 前缀键 → **清空 `_photoCache`**（块变了，照片结果整体失效）。
- **表结构幂等迁移** `EnsureBlockSchema()`（`:1238`）：`ALTER TABLE drawing_blocks ADD COLUMN` `Type` / `BBox` / `Icons`，列已存在则忽略。**必须在缓存早退之前调用**，否则已切图纸永不补齐新列。

### 3.2 调用链路与 CLI 契约

```
DrawingService.EnsureSegmentedCore (:1266)
   ├─ EnsureBlockSchema()                      # 幂等迁移
   ├─ if BlocksCached(did) return              # .done 早退
   ├─ ResolvePhysical(d.VirtualPath)           # 源文件缺失 → .done="empty"
   └─ Process.Start(CreatePythonPsi(segment_blocks.py,
                    "segment", <pdf>, <did>, <segDir>, "200"))
```

CLI 契约（`segment_blocks.py:23-24`）：
```
segment_blocks.py segment <pdf> <did> <out_dir> [dpi]   # 检测+裁切+写 manifest
segment_blocks.py render   <pdf> <did> <out_dir> [dpi]  # 仅渲染整页 {did}_full.png
```
> 第 6 参 `200` 即 **dpi**（C# 生产固定传 200，`segment_blocks_auto.DPI=200` 与之对齐）。

### 3.3 分割算法流程（`segment_blocks.py:157`）

1. **渲染**：`render_page()` 用 PyMuPDF `fitz.Matrix(dpi/72.0, dpi/72.0)` 渲染整页 → `<out_dir>/<did>_full.png`（`:56-61`）。
2. **灰度**：`gray = np.asarray(color.convert("L"))`。
3. **版面检测**：`segment_blocks_auto.detect_auto_regions(pdf, color, gray, W, H, dpi)` → 内部调 `pp_doclayout_onnx.detect()`（**PP-DocLayoutV3 ONNX**，onnxruntime 推理以绕开 AVX2）。原则：**只舍弃不合并**（`:16`）。异常时 fallback v6 并写 stderr。
4. **排序**：`sort(key=(y, x))` 从上到下、从左到右（`:197`）。
5. **裁切**：`color.crop(box)` → `blocks/<did>_blk_NN.png`（`NN` = 序号，两位补零）。
6. **manifest**：写 `blocks/<did>_blocks.json`。
7. **回 C#**：尺寸过滤 → 批量 OCR → `KeepViewBlock` → 入库 → 删弃块 PNG → 写 `.done`。

### 3.4 分割技术参数

**渲染 / 进程**

| 参数 | 值 | 位置 |
|---|---|---|
| `DPI` 默认 | **300**（`segment_blocks.py:41`） | 脚本默认 |
| **生产实际 DPI** | **200**（C# 传参，`segment_blocks_auto.DPI=200`） | `:1284` |
| 渲染矩阵 | `fitz.Matrix(dpi/72, dpi/72)` | `:61` |
| **硬看门狗** | `threading.Timer(100.0, os._exit(1))` → **100s 自退** | `:250` |
| C# 等待 | `WaitForExit(120_000)`，**绝不 Kill** | `:1298` |
| 环境 | 必须 `CreatePythonPsi` 干净环境（顶层 import fitz 原生扩展） | `:1278-1284` |

> ⚠️ **严禁强杀切图子进程**：强杀会毒化原生推理会话，导致此后每次推理确定性崩溃，必须重启才恢复。故依赖脚本自带 100s 看门狗自退（早于 C# 的 120s）。

**版面检测过滤（`segment_blocks_auto.py`）**

| 参数 | 值 | 含义 |
|---|---|---|
| `KEEP_LABELS` | `image` / `figure` / `chart` / `diagram` (`:56`) | 只保留这四类标签 |
| `MIN_SCORE` | **0.60** (`:59`) | 低于此置信度视为噪点 |
| `MIN_AREA_RATIO` | **0.003** (`:60`) | 面积占整页 < 0.3% 的碎块丢弃 |
| `MAX_AREA_RATIO` | **0.40** (`:61`) | > 40% 视为整页轮廓误检，丢弃 |
| `MAX_ASPECT_RATIO` | **10.0** (`:62`) | 长边/短边 > 10 的极端扁长块丢弃 |
| `FRAG_MIN_INNER` | **2** (`segment_blocks.py:85`) | 大框内至少几个小框才触发反向处理 |

**C# 侧块过滤**

| 参数 | 值 | 位置 |
|---|---|---|
| `MinBlockW` / `MinBlockH` | **70 / 70** px（小于此视为噪声碎片，不入库不参与匹配） | `:1210` |
| 批量 OCR | 一次 Python 进程 `BatchOcr(pngPaths)`，规避反复拉起原生进程 | `:1327-1328` |

**`KeepViewBlock`（`:1040`，方案 B 正向选择，严格零候选不降级）**

```
① IsDescriptiveQrFormatBlock(raw)  → 舍弃（前置拦截）
② type == "engineering"            → 保留（R1 几何判据，不依赖 OCR 文本）
③ raw 空白                          → 舍弃
④ HasLabelingText(raw)             → 保留（文本优先，即使 type 为 table）
⑤ type ∈ {table, text_only, spec_format} → 舍弃（R7/R2）
⑥ HasDimensionNumbers(raw)         → 保留（R1 兜底），否则舍弃
```

- `HasLabelingText`（`:1080`）：`ContainsModelIdentifier` ∨ 含「服务热线」∨ `400[-]?\d{7}` ∨ (二维码/QR/NFC/扫码标记 **且** 型号)。
- `HasDimensionNumbers`（`:1066`）：强信号 `[±Φ⌀Ø]\s*[0-9]`、`[0-9]+\s*[±]\s*[0-9]`；弱信号 `\d+\.\d+` / `\d{4,}` / `\d+\s*(mm|cm)`。**不含普通字母 R**（避免 R12 电阻误判）。
- `IsDescriptiveQrFormatBlock`（`:1097`）：命中 8 个描述性短语之一（如「二维码标签激光打标格式」「二维码内容以实际生产为准」）**且**不含 11 个真实打标关键词（`LOW VOLTAGE`/`禁止强电`/`地暖阀`/`DC15/24V`/`服务热线`/`400-`…）→ 舍弃。

### 3.6 失败与兜底

| 情况 | 行为 |
|---|---|
| 图纸/源文件缺失 | 写 `.done = "empty"`，返回 |
| 进程异常 | 写 `.done = "failed"` |
| JSON 为空/反序列化失败 | 写 `.done = "nojson"` + `deser_err.txt`（含 stderr 前 2000 字符） |
| ONNX 检测异常 | stderr 记录并 fallback v6；仍为空则 `mode="auto-none"`，**不回退红框规则**（已移除） |

### 3.7 重过滤 `RefilterDrawing`（`:1448`）

方案 B 兜底：**源 PDF 缺失时**，对已有切块（DB + 磁盘）重新套用 `KeepViewBlock`，并把舍弃块的 `Keep` 置 0。`RefilterAll`（`:1512`）批量执行。

### 3.8 已查证缺陷：`Type` 恒为 `engineering`，块过滤规则退化

**查证结论（2026-09-10，四角度交叉一致）**

| 角度 | 证据 |
|---|---|
| C# 写入 | `:1377` `$type = b.Type ?? ""`，直接取 manifest 的 `BlockEntry.Type`，**无二次分类** |
| Python 产出 | `segment_blocks.py:212` 与 `segment_blocks_auto.py:120` 均**硬编码** `"type": "engineering"` |
| 数据库实况 | `drawing_blocks` 共 **99 块，`Type` 分布 = `[('engineering', 99)]`**，零多样性 |
| 模型能力 | `pp_doclayout_onnx.py:45` 的 `label_list` **本就包含** `table`/`text`/`vertical_text`/`vision_footnote`，`KEEP_LABELS` 也确实用 `label` 做了保留过滤——但过滤后 `label` 被丢弃，未写入 `Type` |

**后果**：`KeepViewBlock`（`:1040`）中规则② `type == "engineering"` **恒为真**，导致：

- 规则③（空文本舍弃）、④、⑤（`table`/`text_only`/`spec_format` 舍弃）、⑥（`HasDimensionNumbers` 兜底）**全部不可达（死代码）**；
- 实际生效的过滤只剩 **`MinBlockW/H ≥ 70`** 与 **`IsDescriptiveQrFormatBlock`**。

**已确认的实际影响**——噪声碎片块未被过滤，参与比对并产出**假「缺标」红框**：

| 回归日志中的假红 | 对应块 RawText |
|---|---|
| `did=106 blk=0` R=2 `red=['zac','i i']` | `'zac\ni i\n1 1'` |
| `did=106 blk=4` R=1 `red=['f 1']` | `'f 1'` |
| `did=119 blk=0` R=2 `red=['rad','国 1']` | `'rad\n国 1'` |

（全库 99 块中，20 块既无尺寸数字也无已知打标文本，其中即含上述噪声块。）

**⚠️ 重要：不可简单删除规则②。** 经验算，若移除规则②让规则⑤⑥生效，`LOW VOLTAGE/禁止强电/地暖阀/DC15/24V` 这类**真实打标块**会被误丢——因为这些关键词**不在** `HasLabelingText` 中（该函数只认型号标识/服务热线/400 电话/二维码+型号），而它们又不含尺寸数字。即：**当前「engineering 恒保留」实际充当了兜底，掩盖了 `HasLabelingText` 覆盖不全的问题**。

**修复方向（须先补齐判据再启用过滤）**
1. 首选：把 ONNX 已产出的 `label` 写入 `Type`（`table`/`text`/…），使规则⑤⑥恢复语义；
2. 或将 `LOW VOLTAGE`/`禁止强电`/`地暖阀`/`DC15/24V` 等真实打标关键词补入 `HasLabelingText`，再放开规则②；
3. 二者皆需以全量回归（27 图 + 99 块）守门，确认假红减少且真实打标块零丢失。

## 4. 核心业务流程（照片比对）

### 4.1 主流程 `match-block`（H5 实际使用）

`DrawingModule.cs:86` → `DrawingService.MatchBlock`（`:1717`）

1. **照片缓存**：键 `drawingId_MD5(照片)`（`:1724`）。命中且已有 Diff → 秒回；命中缺 Diff → 补算 diff。
2. **保存照片**：按 MD5 命名写 `data/seg/<did>/match_<md5>.jpg`。
3. **降采样**：`resize_photo.py` 缩到最长边 **960**（`:1763-1788`）。
4. **EnsureSegmented**：见 §3。
5. **OCR**：`_ocr.Recognize(photoPath)` → 常驻 worker → `ocr_cli.main` → `_auto_roi`。
6. **质量门控**：`IsPhotoMeaningful`，不通过返回「无法识别照片内容」。
7. **匹配**：`MatchBySimpleText` → `full / partial / none`。
8. **差异**：`Task.Run(ComputeDiffFromPath)` 与入库并行，随后 `await` 取回（`:1839`/`:1860`）。
9. **入库**：`drawing_histories`，并写回 `_photoCache`。

> `ocr_cli._auto_roi`：全图 RapidOCR → 文本行聚类 → 取最佳簇 → **裁剪 + LANCZOS 2× 放大 → 二次 OCR**；质量退化则回退首次结果（方案A，97ba42a）。

### 4.2 合并端点 `match-and-photo`

`DrawingModule.cs:101` → `MatchAndPhoto`（`:1991`）：一次请求完成「块匹配 + 照片标示 + 快照入库」，经 `OcrService.CombinedDiff`（`:2045`）在**常驻 worker** 内跑 `run_on_photo`。

### 4.3 两条 Python 通路（关键区别）

| 通路 | 进程模型 | 用于 |
|---|---|---|
| `OcrWorkerClient.CombinedDiff` | **常驻 worker**（stdin/stdout 行式 JSON，引擎只加载一次） | `match-and-photo` → `run_on_photo` |
| `ComputeDiffFromPath` | **每次请求新建子进程** | `match-block` 单块 diff → `run()` |

### 4.4 照片标示 `run_on_photo`（全块）

`diff_visualizer.py:3324`，默认 `max_out=2000, photo_ocr_max_dim=800, enable_lcd_geocheck=True`。
流程：读图 → 限最长边 `_MAX_WORK=2000`（`:3373`）→ deskew（`max_dim=480`，`:3410`）→ 坐标空间统一 → **照片 tiled OCR**（`:3429`）→ **逐块 OCR 前置缓存**（`_BLOCK_OCR_CACHE` by mtime，`:3436-3454`）→ 块定位 → 照片图标检测 → LCD 屏显检测 → 逐块 `_compare_block` → **v19.56 灰化二次救援**（`:3571-3589`）→ 判定与绘制。

### 4.5 单块比对 `run()`

`diff_visualizer.py:2837`，位置参数契约（`ComputeDiffFromPath:2790-2795`）：
```
diff_visualizer.py <photo> <blockPng> <outFile> <bboxCache> <blockRawText> <photoText> "" <icons>
```
photo 模式契约（`:2627`）：
```
diff_visualizer.py photo <inFile> <did> <outFile> <db_path> <seg_root>
```
第 4/5/6/8 参为「免 OCR」override（块 bbox、块 RawText、照片文本、图标框），命中即跳过对应 OCR/检测。

| 块 bbox / 图标框 | 内存 L1 + DB 持久化 |
| 分割缓存 | `data/seg/<did>/.done` |
| 连续 Tesseract fallback 自愈 | 阈值 2 次 → Kill worker 重建 |

### 6.6 颜色语义

| 颜色 | 含义 |
|---|---|
| 🔴 红 | 缺标（块有、照片无） |
| 🟡 黄 | 多标 / 图标差异 |
| 🟢 绿 | 一致 |
| ⚪ 灰 | 跳过（CAD 文字、LCD 屏显、图标内噪声） |
| 状态 | `full`/`partial`/`none`；块级另有 `low_conf`（照片未定位到该块） |

| 阶段 | 960 px（生产） | 1920×2560（原图） |

**已修复（2026-09-07）**：`resize_photo.py` 被 60a4884「优化文件结构」归档，而 C# 为硬编码路径 + `File.Exists` 静默跳过 → 照片按原图送 OCR → 超时。已恢复脚本（含 `convert("RGB")` 防异常被 `catch{}` 吞掉），链路 25.9 s → 8.05 s。

## 10. 部署与运维要点

- **改 .py 即时生效**（常驻 worker 除外）：worker 内 `import` 会缓存，改 `ocr_cli.py`/`diff_visualizer.py` 后须确认 **Platform 进程 StartTime > .py mtime**，否则验证的是旧代码。
- `resize_photo.py`、`segment_blocks.py`、`diff_visualizer.py` 均由 C# **新建子进程**调用 → **无需重启**，下次请求生效。
- 改 C#：Stop `SCG_Platform` → `dotnet build -c Debug` → Start。
- **分割子进程绝不强杀**（毒化原生推理会话，需重启恢复）。
- 自愈：worker 超时/异常 → `KillWorker()` 重建；连续 2 次 Tesseract fallback → 重建。

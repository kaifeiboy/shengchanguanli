## 一、为什么"改了 A 坏 B" —— 系统性归纳

| # | 系统性问题 | 表现 | 历史补丁 | 补丁引发的回归 |
|---|---|---|---|---|
| **P1 规则叠加 vs 互殴** | 6 个独立过滤函数（`_is_cad_annotation` / `_is_cjk_garbage` / `_is_lcd_display_text` / `_is_annotation_note` / `_is_qr_ocr_noise` / `_is_serial_number`）相互交叉，每个都维护独立白名单/黑名单 | 改一处必须连锁改 5 处 | v19.33→v19.35 三连修只为"长按取消" / "禁止强电"不被误灰 | v19.34 加「禁止」→19.35 又得删「禁止」→19.34 选「定时」→19.34 又得删「定时」 |
| **P2 OCR 误检/漏检 → 图标级联崩** | `_detect_icon_regions` 有 7 个独立子检测器（zxing / pyzbar / `_qr_finders` / `_dense_rects` / strict cluster / loose cluster / icon-edge-density / icon-aspect-ratio），每个都可能误检 | 报告 4 截图里有 3 处是图标相关（did=132 假黄/照片 QR 漏/did=115 A 字符当图标） | v19.25→v19.32 共 8 个图标专项补丁 | 每改一处检测器灵敏度，3-4 个其他规则同时失灵 |
| **P3 DB 持久化污染** | `DrawingService.ComputeDiffFromPath` 把 `block_icons` / `block_lines` 写回 DB `drawing_blocks` 表，重启后污染下一轮调用 | did=132 blk_0 因历史 `Icons='[]'` 被当 override；did=115 blk_3 因假图标 `[226,266,16,16]` 入库 | v19.37 改 truthy 判断 | 仍可能再写入新污染值（v19.37 没清理历史脏数据） |
| **P4 匹配语义模糊** | "红/黄/绿/灰/紫" 5 类语义重叠；OOB 坐标静默失败（用户看不到但 JSON 污染） | did=115 blk_1/2/4 yellowRegions 含 `(594,861,174,37)` 大坐标，画到块图溢出 | 仅排查发现，没动代码 | 长期存在，用户举报才暴露 |
| **P5 OCR 引擎对小字符漏读（最本质）** | RapidOCR det 模型对 <12px 小字符不敏感，全图漏读；同样字符在裁 ROI 后能读出 | did=115 blk_3 的 A·B 漏读是**根因**：①导致块侧无 A·B → DB 不入库 → ②导致 photo 读出"AB" vs 块侧空 → ③触发假黄框 + 假红框 + 假紫框 3 个差异 | 仅报告，未根除 | 整类问题未修 |
| **P6 缺少"语义等价"层** | 所有匹配走字符串 LCS/Jaccard；产品规格"DC15/24V"和"DC15-24V"是产品不同型号，匹不匹配需要业务理解 | 当前用 OCR 字符串相等，与"产品上打的标对不对"语义完全脱节 | 不存在 | 长期存在 |

**根因归纳**：当前是「**特征级规则堆叠**」而不是「**业务级语义匹配**」——22 张图纸里有 ~12 类典型问题，每类又有 3-5 个边界场景，每个边界都要写新规则，规则叠加又互相打架。

## 三、三条根治路线

### 方案 A：方案 B 加有限重切（全自动数据重生 + 自适应规则集）
**前提**是用户接受"全量重切一次"（约 10 分钟 + 全量回归 30 分钟）

**内容**：
1. **全量 22 图重切**：以 Phase1 ROI 切图算法（v19.18 已验证）重做 22 图共 99 个块，写回 `drawing_blocks.RawText` 与 `Icons=[]`（强制清空所有历史图标污染，**不存任何由自检产生的伪图标**）。
2. **小幅提速规则替换**：
   - 删 `_is_annotation_note` / `_is_lcd_display_text` / `_is_cjk_garbage` 三个独立函数 → 合并成单一 `_is_business_garbage(text, has_anchor: bool)` 函数：
     - `has_anchor=True`（参考侧白名单有同锚词）→ 放行；
     - `has_anchor=False` → 进入"待 OCR 二次确认"队列（不再硬判灰化）。
   - 保留 `_is_serial_number` / `_is_qr_ocr_noise` / `_norm_text` 三个高价值规则。
3. **保留 v19.36/19.37 的两处修复**（QR size 30%/18% 分场景 + truthy override 判断）。
4. **护栏**：每次改动后跑 `real_match_regression.py` 99 块 → **要求 R+Y 总和不超过 v19.37 baseline（48 块）**，且 R 单独不超 30。

**工作量**：3-5 天（含全量回归 + 4-5 轮迭代调优）。
**风险**：低。核心规则保留，改的是规则**叠加方式**（从 5 个独立函数 → 1 个统一函数 + 锚点确认）。
**收益**：根治 P1（规则互殴），P3（DB 历史污染一并清空），P4（OOB 静默失败顺手补 if x+y+w<blockW 校验）。

---

### 方案 B：方案 A + 业务级匹配模型（全量重切 + 「语义等价」匹配层）
**前提**是用户接受「重写匹配」+「样本积累期」

**内容**：
1. **方案 A 全部内容**。
2. 在匹配前插一层「**业务等价词典**」：
   - 产品码白名单：`QHR45/QHRW6/8EQ0024/B280001/2005120635` 等已知真实序列号 ✓
   - 产品码黑名单：`200512/DC15/24V/74U119I` 等已知非序列号 ✗
   - 规格等价表：`DC15/24V ≡ DC15-24V`（同一产品多写法）
   - 字符级容错：`A ≡ A·B ≡ "A B" ≡ "A.B" ≡ "A，B"` 等。
3. 词典来源：人工**整理 22 图**所见真值，每图 5 分钟 = **3 小时**一次性投入。
4. 写 `model/business_equivalence.py` 持久化。
5. 匹配前查表 → 同义则绿框 / 异义才走精细匹配。

**工作量**：A 的 3-5 天 + 额外 3 小时整理 + 2 天写代码。
**风险**：中。整理词典靠人工，可能漏；需"22 图对一遍"的样本复核。
**收益**：根治 P5（OCR 漏读 → 业务词典保底）+ P6（语义等价）。

---

### 方案 C：架构级重写（OCR+图标+匹配 三段解耦 + ground truth DB）
**前提**是接受「长期重构 + 完整测试」

**内容**：
1. **OCR 段**：`run()` 不直接调 RapidOCR，而是组装 `(photo_ocr, block_ocr) = ocr_pipeline.run(photo, block)`：
   - 全图 OCR → ROI 重检（<16px 字符）→ 二次合并 → bbox 收敛。
   - 输出：**统一 schema** `{"lines": [{"text": str, "bbox": [x,y,w,h], "conf": float, "level": "primary"|"roi"}]}`。
2. **图标段**：`icon_pipeline.run(photo, block, ocr_lines)` 返回**结构化图标列表**：
   - 每图标 `{kind: "QR"|"NFC"|"logo"|"other", bbox, evidence: [...], confidence}`。
   - **永远不返回 "可能是 QR"**——只有"已确认 QR (zxing 解码成功)"/"非图标区域 (OCR 文本区)"二分。
3. **匹配段**：`match_pipeline.run(photo_lines, block_lines, photo_icons, block_icons)` 走「**锚点+容差+语义等价**」三段式匹配，完全替代当前的 `_texts_match_strict`。
4. **DB 作为 ground truth**：
   - 切图阶段固化 `RawText`（带 bbox 缓存）。
   - 图标不固化，由 live 检测。
   - 增加 `MatchAnchors` 表（手工标注的金标准锚点，22 图一次性标全）。
5. **完全废弃** `silentSkipped` / `cadOnly` / `blockExclusive` 等含糊字段。

**工作量**：2-3 周。**伴随 22 图金标准标注**（1-2 天）。
**风险**：高。需要完整重测 + 新测试用例。**与现有 99 块回归套件不能直接复用，需新套件**。
**收益**：一次性根治 P1-P6 全部。后续增加新图/新产品不再触发"打地鼠"。

## 五、全量 selfblock 扫描实证（决定性证据，2026-08-03 18:35）

> **测试设计**：photo = block = 同一张 CAD 切块。理想结果 = **0 红 0 黄 0 图标差异**。
> **实际结果（v19.37, 99 块）**：

| 指标 | 值 | 评估 |
|---|---|---|
| R（缺标假阳）| **15** | ❌ |
| Y（多标假阳）| **10** | ❌ |
| **IconMissing 假阳** | **30** | ❌ **核心问题** |
| IconExtra 假阳 | 2 | ❌ |
| G（正确匹配）| 577 | |
| OOB 0、错误 0 | | ✅ |

**99 块中 40 块（40%）自检就有差异**——直接证明这是规则本身的系统性问题。**而且 75% 的假阳是图标相关**。

### 五大问题模式（按影响块数排序）

| 模式 | 块数 | 根因 | 影响方案 |
|---|---|---|---|
| **A 自检就报 iconMissing** | 30 | `_detect_icon_regions` 把非图标密集区域当成 QR 候选 | A/B/C 全部受益（C 收益最大） |
| **B 自检 R1Y1 对称假阳** | 9 | step3 / step4 匹配规则的字符级 diff 在"两侧都有但不相同"时同时报缺+多 | A/B/C 全部受益 |
| **C 自检 R2 单纯缺标** | 2 | 文本内容两侧有大小/方向差 → 字符级不匹配 | A/B/C |
| **D 自检 R1 单纯缺标** | 2 | 单字符 OCR 不稳定 | A/B/C |
| **E 自检 iconExtra** | 2 | iconMissing 反向（块图无，block_text_override 有差异） | A/B/C |

### 关键洞察：图标问题是真正的"症状之王"

用户原话"图标识别标示的问题最多" → **30/40 块（75%）都是图标假阳** → **根治图标 = 根治 75% 的"修 A 坏 B"现象**。

具体而言：
- `_detect_icon_regions` 函数有 **6 个独立检测器**（zxing decode / pyzbar decode / `_qr_finders` / `_dense_rects` / strict cluster / loose cluster），每个都可能误检。
- 即使 selfblock 时把 photo 和 block 都设为同一个图（这种情况下应该 0 图标差异），仍检出 30 个"块有图标但 photo 没有"——**说明检测器本身就有 30% 的假阳率**。

### 净化策略（任何方案都建议先做）

**Zero-step**（任何方案执行前先做这一步）：
1. 全量 22 图重切：清空所有 DB `Icons`（避免历史伪图标持久化）
2. selfblock 二次扫描验证：必须 ≤ 5% 假阳率（从 40% 降到 5%）
3. 通过后再做方案 A/B/C 的实质改动
